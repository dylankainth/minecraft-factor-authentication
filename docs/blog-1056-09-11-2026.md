## What changed this session

1. Built `redstone_parts.py` — a helper library for composing circuits
   (standing-torch NOT, raw lever tap, repeater `travel()`/`converge()`,
   diagonal dust "staircase" for changing height without a gate). This
   encodes every empirical MCHPRS finding to date so a future circuit can't
   silently reintroduce an already-fixed bug.
2. Added collision detection to `Schematic.set()` in `schem.py` — it used to
   silently let two parts of a circuit overwrite each other at the same
   coordinate, which was a real source of hard-to-diagnose bugs.
3. Found and fixed a new, real MCHPRS behavior (not a mistake in this repo's
   code, a property of the simulator): **a redstone dust cell that is itself
   the landing point of a diagonal "staircase" step does not reliably power
   a directly-adjacent consumer block** (a lamp, or a stone block with a
   torch on it being used as a NOT-gate's input). The dust's own power value
   reads correctly, and it CAN power another plain dust cell fine — but a
   lamp or torch-support block placed immediately off the landing cell
   itself does not register as powered, ever, regardless of the dust's power
   level. Isolated with `build_rawb_lamp_test.py` (surrounded a staircase
   landing cell with lamps on all 4 horizontal sides plus straight up — only
   the one directly above lit correctly, tracking the lever on/off/on/off).
   Confirmed the fix with `build_rawb_fix_test.py`: insert one plain
   (non-diagonal) dust hop between the staircase landing and anything that
   needs to read its power. That one extra hop reads the correct decayed
   power and correctly powers a lamp.
4. Applied that fix to `build_xor_compact_test.py`'s two merge points (S1 and
   S2 — see `redstone_parts.py`'s module docstring and the XOR file's own
   docstring for the gate identity being built:
   `XOR(A,B) = OR(Term1, Term2)`, `Term1 = NOT(NOT_A OR raw_B)`,
   `Term2 = NOT(raw_A OR NOT_B)`). This took the live truth table from 0/5
   correct states to 4/5.

## Infrastructure notes for whoever continues (don't rediscover these)

- MCHPRS container: `mchprs`, network `totp-net`, port 25565 bound to
  localhost only. World/schematic data lives in `./mchprs_data` (gitignored,
  not committed). Any `docker run` with a `-v` mount from Git Bash on
  Windows needs `MSYS_NO_PATHCONV=1` prefixed, or the path gets silently
  mangled and the mount breaks.
- Bot image: `totp-bot:local`, built from `bot/Dockerfile`. **Always
  `docker build` after editing any `bot/*.js` file** before `docker run` —
  stale-image reruns of an edited script is a real mistake that happened
  this session.
- Probes anchor relative to the bot's own natural spawn position
  (`bot.entity.position.floored()` after a ~3s settle, then a small offset
  like `+5,+0,+5`) — never a large distant absolute coordinate. Big
  teleports leave `bot.blockAt()` returning `null` indefinitely because
  chunk streaming is driven by actual gradual movement, not claimed
  position. Use `/tp` (small hop) + `bot.creative.startFlying()` + a short
  loop manually re-pinning `position`/`velocity` to hold still — don't use
  `bot.creative.flyTo()`, it's been seen to drift indefinitely.
- `mineflayer`'s `'spawn'` event never fires against MCHPRS (it waits on a
  packet MCHPRS doesn't send) — listen for `'login'` instead.
- `Schematic.save()` in `schem.py` normalizes every coordinate to
  `min(x/y/z)` across ALL blocks in the schematic, not to 0 and not to
  whatever you consider the "anchor" block. When a probe's coordinates look
  right but reads come back wrong/air, don't trust hand-computed offsets —
  write a 3-line Python snippet that builds the real `Schematic` object and
  prints `min(p[i] for p in s.blocks)` directly, then compute local offsets
  from that.
- A pasted circuit's torches/dust keep exactly the blockstate you wrote —
  nothing is recomputed from neighbors on paste, not even by WorldEdit's
  `//update`. Always drive every input through at least one real toggle
  before trusting any read from a freshly-pasted circuit.
- Standing torches (`redstone_torch`) work as inverters; wall torches
  (`redstone_wall_torch`) do not reliably cascade power past their first
  dust neighbor in this build — use standing torches always.
- A repeater's `facing` property names the direction power *enters* from,
  not outputs to (opposite of the usual vanilla mental model). Repeaters are
  strictly straight-through — no 90° turns; only dust can bend a corner.
- Never let two independently-driven sources merge through a shared dust
  cell — it silently fails to power anything downstream. Route each source
  through its own repeater and aim both repeater outputs directly at the
  same consumer block from different sides (`redstone_parts.converge()`
  does this correctly already — use it, don't hand-roll a dust merge).
- **New this session, now baked into `redstone_parts.step()`'s docstring
  but worth repeating**: never connect a staircase landing cell directly to
  a lamp or a torch-support block. Always route through one more plain dust
  hop first.
